"plumix": minor
---

`plumix migrate` now applies every table owner's shipped migrations: core's, then each plugin package's in config order, then the site's own `migrations/` when it has one. Each owner records what it applied in its own `__drizzle_migrations_<owner>` table, so a plugin installed later still gets its older migrations. `plumix migrate fresh` deletes the local database and applies everything again, and `plumix migrate status` lists each owner's applied and pending migrations. The first `plumix migrate` against a database built by `migrate generate` and `migrate apply` adopts it without running any DDL when its schema matches, and refuses with every difference listed when it does not. Removes `plumix migrate apply`; `plumix migrate generate` is unchanged. The command `definePlumixE2EConfig` bakes for a playground is now `plumix migrate fresh` then `plumix dev`, so an e2e run no longer deletes a committed `drizzle/`. Removes the `applyMigrations` option from `definePlumixE2EConfig`, adds `sharedDatabase: false`, and `plumixDbBaseline` leaves the tracking tables alone. A runtime's commands module now exports `migrations`, which opens its database for `plumix migrate`, in place of the `migrate` subcommand registry.
