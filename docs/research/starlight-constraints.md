# What Starlight can express structurally

Research for [#1832](https://github.com/withplumix/plumix/issues/1832), under the docs
information-architecture map [#1829](https://github.com/withplumix/plumix/issues/1829).

The question: what can Astro Starlight actually express, and where would an IA spec be
asking for something Starlight cannot give without custom work?

## Constraints that bind the spec

1. **A sidebar group's label is not a link, and cannot be made one.** Source-verified: the
   group schema has `label` + `items` and no `link`/`slug`. The Laravel pattern of "a section
   whose first page is Getting Started" is expressible only as an inert heading followed by a
   page named _Getting Started_ — the section header itself is dead text.
2. **"Two levels deep" is a discipline, not a guardrail.** Group nesting is recursive and
   uncapped in the schema, and core's `autogenerate.depth` option is commented out in source.
   Nothing fails when a third level appears. A manual sidebar array makes a third level visible
   in review diffs; that is the only zero-dependency enforcement available.
3. **`draft: true` gives the map exactly the "P1–P2 absent rather than stubbed" behaviour it
   asked for** — but only with an autogenerated sidebar. A manual sidebar entry pointing at a
   drafted-out page throws `AstroError` and fails the production build. Sidebar shape and
   shipped-page set become one coupled edit.
4. **Frontmatter shape is enforceable; body shape is not.** `docsSchema({ extend })` can add
   required fields and tighten built-ins. Nothing first-party validates that a page opens with
   narrative and closes with a roster. The available seam is `routeMiddleware`, which runs for
   every rendered page and can read `headings`, and throwing there fails `astro build`.
5. **Four separate needs push pages to `.mdx`:** tabs, partials, `?raw` code imports, and inline
   `<Badge>`. Plain `.md` gets asides, Expressive Code and headings — nothing else. The spec
   should probably just declare `.mdx` everywhere, which invalidates the "markdown-only, no
   custom `.astro` components" premise in `apps/docs/README.md`.
6. **Versioning is a community plugin, and it is folder-copy versioning.** `starlight-versions`
   duplicates the whole of `src/content/docs/` per archived version. At ninety pages that is
   ninety files per version, plus a linearly growing Pagefind index.
7. **Code samples can come off disk, but only whole files.** `?raw` + `<Code>` is first-party
   and documented. Region or line-range extraction is not; slicing happens in the MDX frontmatter
   script or a custom remark plugin.
8. **Search and i18n both ship first-party and cost nothing to leave on.** i18n is the one that
   is expensive to adopt _late_ — see [§6](#6-search-and-i18n).

## 1. Sidebar

Primary sources: [sidebar guide](https://starlight.astro.build/guides/sidebar/),
[configuration reference](https://starlight.astro.build/reference/configuration/), and
[`packages/starlight/schemas/sidebar.ts` at `0.41.3`](https://github.com/withastro/starlight/blob/%40astrojs/starlight%400.41.3/packages/starlight/schemas/sidebar.ts).

### The item union

A sidebar item is one of five things:

- a **shorthand string** — a docs-collection slug;
- an **internal link** — `{ slug, label?, badge?, translations?, attrs? }`;
- an **external/explicit link** — `{ link, label, badge?, translations?, attrs? }`;
- a **manual group** — `{ label, items, collapsed?, badge?, translations? }`;
- an **autogenerate block** — `{ autogenerate: { directory, collapsed?, attrs? } }`.

### Nesting depth

Unlimited. `ManualSidebarGroupSchema` is defined with `z.lazy()` and lists itself in its own
`items` union, so groups nest arbitrarily. There is **no depth cap and no way to ask for one**:

```ts
// TODO: not supported by Docusaurus but would be good to have
/** How many directories deep to include from this directory in the sidebar. Default: `Infinity`. */
// depth: z.number().optional(),
```

That commented-out option is inside `AutoSidebarEntriesSchema` at `0.41.3`. Consequence for the
map's "two levels deep, everywhere": with `autogenerate`, any subdirectory someone adds under a
section directory silently becomes a third level. Core cannot stop it.
`starlight-auto-sidebar` supplies a `depth` property (see below).

### Manual vs autogenerate

`autogenerate: { directory }` walks a docs subdirectory and builds links, creating a nested group
for every subdirectory it finds. As of Starlight `0.39.0` an `autogenerate` block **cannot carry
its own `label`** — the schema explicitly rejects it with a migration error and tells you to wrap
it: `{ label: 'X', items: [{ autogenerate: { directory: 'x' } }] }`.

The two approaches differ in a way that matters here:

| | Manual array | `autogenerate` |
| --- | --- | --- |
| Order | array position | `sidebar.order` frontmatter, ties broken by slug |
| `sidebar.hidden` frontmatter | ignored | respected |
| `draft: true` page | **build error** if referenced | silently skipped |
| Third level appears | only if someone writes it | automatically, from any subdirectory |
| Where the tree lives | `astro.config.mjs` | the filesystem |

`sortDirEntries()` — the function that reads `sidebar.order` — is only reached from
`groupFromDir()`, i.e. the autogenerate path. **`sidebar.order` does nothing in a manual
sidebar.**

### Collapsed groups

`collapsed: boolean`, default `false`, on manual groups and on `autogenerate` (where it applies
to generated subgroups). Starlight persists the open/closed state client-side.

### Badges

`badge: string | { text, variant?, class? }`, with
`variant: 'note' | 'danger' | 'success' | 'caution' | 'tip' | 'default'`
([`schemas/badge.ts`](https://github.com/withastro/starlight/blob/%40astrojs/starlight%400.41.3/packages/starlight/schemas/badge.ts)).
A bare string gets the `default` variant, which uses the site accent colour.

Badges are available on links, on groups, and via `sidebar.badge` frontmatter. The `class`
escape hatch means **the map's P0/P1/P2 tiers are directly expressible as sidebar badges**
with three custom CSS classes — a capability the map has not considered. `translations`/i18n
badge text is supported too (`{ text: { en: 'New', uk: 'Нове' } }`).

Note: groups explicitly reject `attrs` — the schema sets `attrs: z.never().optional()` with a
comment explaining it is there because TypeScript will not excess-property-check a
non-discriminated union. Only links take HTML attributes.

### Can a group label be a page?

**No.** The group schema is `label`, `translations`, `badge`, `attrs: never`, `collapsed`,
`items`. There is no `link` or `slug` field, and no first-party option to make a group header
navigable.

Three workarounds, in increasing cost:

1. Make the first item of each group the section's landing page — `{ slug: 'blocks/index', label: 'Getting Started' }`. This is what the Starlight docs site itself does and what the Laravel pattern in the map's Notes reduces to.
2. `starlight-auto-sidebar` `_meta.yml` files, which let the *directory* carry `label`, `badge`, `collapsed`, `order`, `sort`, `hidden`, `depth` and `cascade` — still no link on the group header, but the section metadata moves out of `astro.config.mjs` and into the filesystem next to the pages.
3. [`starlight-sidebar-topics`](https://github.com/HiDeoo/starlight-sidebar-topics) (HiDeoo), which replaces the single sidebar with per-topic sidebars where each topic **does** have a required `link`. This is a different navigation model — a topic switcher above a topic-scoped sidebar — not a fix for group headers. Worth naming only if the ninety-page tree turns out to want two audiences with separate trees, which is exactly what the map's "two, and only two" audiences hints at.

### Community plugins named

| Plugin | Author | Latest | Peer range | Status |
| --- | --- | --- | --- | --- |
| [`starlight-auto-sidebar`](https://github.com/HiDeoo/starlight-auto-sidebar) | HiDeoo | `0.4.0` (2026-05-07) | `@astrojs/starlight >=0.39.0` | maintained, compatible |
| [`starlight-links-validator`](https://github.com/HiDeoo/starlight-links-validator) | HiDeoo | `0.25.3` (2026-08-12) | — | actively maintained |
| [`starlight-sidebar-topics`](https://github.com/HiDeoo/starlight-sidebar-topics) | HiDeoo | — | — | maintained |

`starlight-links-validator` is worth flagging to the map: it fails the build on broken internal
links and (optionally) missing heading anchors. Given ninety hand-written cross-linked pages and
the map's acknowledged roster-drift problem, this is the cheapest structural guard on offer and
it is not currently in the plan.

## 2. Versioning

**Not first-party.** Starlight has no versioning of any kind. The only real option is
[`starlight-versions`](https://github.com/HiDeoo/starlight-versions) by HiDeoo
(<https://starlight-versions.vercel.app>).

Maintenance status: **actively maintained.** `starlight-versions@0.10.0` published 2026-08-21,
`0.9.1` 2026-07-07, `0.9.0` 2026-05-08. MIT. `peerDependencies: { "@astrojs/starlight": ">=0.39.0" }`,
`engines.node >=22.12.0` — compatible with the pinned `0.41.3`. The README still carries the
author's own warning: _"an opinionated plugin that is still in early development. Expect frequent
updates and changes."_

### How it works

Folder-based versioning, by the plugin's own taxonomy (it documents branch- and tag-based
alternatives and explains why it did not pick them). The current version always lives at
`src/content/docs/`. You declare a version in config, start the dev server, and the plugin
**archives the current tree by copying it**:

```js
starlightVersions({
  versions: [{ slug: '2.0' }, { slug: '1.0' }],
})
```

Before, after creating `1.0`:

```
src/content/docs/{configuration.md, getting-started.md, index.mdx}
src/assets/images/preview.png
->
src/content/docs/1.0/{configuration.md, getting-started.md, index.mdx}
src/content/docs/{configuration.md, getting-started.md, index.mdx}
src/assets/images/1.0/preview.png
src/assets/images/preview.png
```

Pages, assets **and the sidebar configuration** are archived per version. It also requires a
second content collection in `src/content.config.ts`:

```ts
import { docsVersionsLoader } from 'starlight-versions/loader'
export const collections = {
  docs: defineCollection({ loader: docsLoader(), schema: docsSchema() }),
  versions: defineCollection({ loader: docsVersionsLoader() }),
}
```

Config surface: `versions[]` (each with `slug`, optional `label`, optional
`redirect: 'same-page' | 'root'`), `current: { label, redirect }`, and `exclude: string[]` —
globs relative to `src/content/docs/` for pages that should always show latest content
regardless of selected version. `exclude` is the release valve for pages that must never fork
(a changelog, a support-policy page).

### What it costs

- **Repo layout.** Full duplication of the docs tree per archived version. Ninety pages means
  ninety more files per version, and every one of them is a copy that no longer tracks changes
  against its source — the plugin says so itself.
- **CI.** Build time and Pagefind index size scale linearly with version count; the plugin
  overrides Starlight's `Search` component to scope results per version.
- **Authoring.** A fix that applies to all versions must be applied to each copy by hand.

### Reconciling with what `apps/docs/README.md` already commits to

The README states the intent: _"inline 'Added in x.y' badges pre-1.0; `starlight-versions`
snapshots per major from 1.0."_ Both halves check out.

The pre-1.0 half needs a caveat the spec should absorb: a Starlight `badge` is a **sidebar**
badge attached to a whole page. An "Added in 0.7" marker on one row of a roster needs the
`<Badge>` component inline, which is MDX-only, or an aside. That is an authoring convention, and
it is one more force pushing every roster page to `.mdx`.

Given the map's target of ninety pages and Plumix's pre-1.0 breaking-minor cadence, the honest
reading is: **do not turn versioning on before 1.0.** Snapshotting each breaking minor would
multiply the tree several times over before the first stable release.

## 3. Page-level structure

### Frontmatter schema

Full set at `0.41.3`
([`packages/starlight/schema.ts`](https://github.com/withastro/starlight/blob/%40astrojs/starlight%400.41.3/packages/starlight/schema.ts),
[frontmatter reference](https://starlight.astro.build/reference/frontmatter/)):

| Field | Type | Default |
| --- | --- | --- |
| `title` | `string` | **required** |
| `description` | `string?` | — |
| `editUrl` | `url \| boolean` | `true` |
| `head` | `HeadConfig[]` | `[]` |
| `tableOfContents` | `false \| { minHeadingLevel, maxHeadingLevel }` | inherits global |
| `template` | `'doc' \| 'splash'` | `'doc'` |
| `hero` | `HeroConfig?` | — |
| `lastUpdated` | `Date \| boolean` | inherits global / git |
| `prev`, `next` | `boolean \| string \| { link?, label? }` | inherits |
| `sidebar.order` | `number?` | — (autogenerate only) |
| `sidebar.label` | `string?` | falls back to `title` |
| `sidebar.hidden` | `boolean` | `false` (autogenerate only) |
| `sidebar.badge` | `string \| BadgeConfig` | — |
| `sidebar.attrs` | `Record<string, string \| number \| boolean>` | `{}` |
| `banner` | `{ content: string }?` | — |
| `pagefind` | `boolean` | `true` |
| `draft` | `boolean` | `false` |

`draft` is filtered in `utils/routing/index.ts`:

```ts
await getCollection('docs', ({ data }) => {
  // In production, filter out drafts.
  return import.meta.env.MODE !== 'production' || data.draft === false;
})
```

Drafts render in `astro dev` and vanish from `astro build`. **This is precisely the map's
"ships with P1–P2 pages absent rather than stubbed", available for free** — with the manual-sidebar
caveat in [§1](#1-sidebar) and constraint 3 above. `navigation.ts` throws on an unresolvable slug:

> `The slug "…" specified in the Starlight sidebar config does not exist.`

### Table-of-contents depth

Global `tableOfContents: false | { minHeadingLevel, maxHeadingLevel }` and the same shape per
page in frontmatter. Defaults `{ minHeadingLevel: 2, maxHeadingLevel: 3 }`; each bound is an
integer 1–6, and a `.refine()` rejects `min > max`
([`schemas/tableOfContents.ts`](https://github.com/withastro/starlight/blob/%40astrojs/starlight%400.41.3/packages/starlight/schemas/tableOfContents.ts)).

This is directly relevant to the map's page shape. A Laravel-validation-shaped page — narrative
then a long roster where each item is an `h3` — produces a very long ToC at the default `2–3`.
`maxHeadingLevel: 2` per page turns the ToC into a section index instead of an item index. The
spec should decide this once, globally, rather than leave it to authors.

### Can a house page template be enforced?

**Frontmatter: yes. Body: not by Starlight.**

`docsSchema({ extend })` intersects the user schema with Starlight's:

```ts
UserSchema
  ? StarlightFrontmatterSchema(context).and(UserSchema)
  : StarlightFrontmatterSchema(context)
```

Because it is an intersection, extending with `z.object({ description: z.string() })` makes the
built-in optional `description` **required**, and new required fields are additive. So a spec can
enforce, at build time, that every page carries e.g. `tier: 'P0' | 'P1' | 'P2'` and an audience
tag, and that `description` is present.

**Two bugs in the pinned version bear on this.** Both are fixed in patches `apps/docs` has not
taken ([changelog](https://github.com/withastro/starlight/blob/main/packages/starlight/CHANGELOG.md)):

- `0.41.4` — _"Fixes support for modifying Zod enums when passing an `extend` option to Starlight's `docsSchema()`"_ ([#3936](https://github.com/withastro/starlight/pull/3936))
- `0.41.5` — _"Fixes a regression when using a union to extend Starlight's `docsSchema()`"_ ([#4095](https://github.com/withastro/starlight/pull/4095))

If the spec wants a discriminated union of per-shape frontmatter (concept page vs roster page vs
reference page), **bump `@astrojs/starlight` to `>=0.41.5` first.** It is a patch bump within the
existing `^0.41.3` range, so `pnpm update` suffices — but the spec should say so explicitly rather
than assume.

For body structure, the seams are:

- **`routeMiddleware`** ([route data guide](https://starlight.astro.build/guides/route-data/),
  [reference](https://starlight.astro.build/reference/route-data/)) — `defineRouteMiddleware()`
  runs on every page render and receives `context.locals.starlightRoute`, which exposes `entry`
  (frontmatter and body) and `headings: { depth, slug, text }[]`. Throwing inside it fails a
  prerendered build. This makes "every roster page must contain an `h2` titled _Available field
  types_" mechanically checkable. It is not what the feature is advertised for, and the docs do
  not discuss validation use, so this is custom work — but small custom work in a supported API.
- **A repo-side check.** A vitest suite over `src/content/docs/**` is the alternative and keeps
  the failure out of the render path.
- **Component overrides** ([guide](https://starlight.astro.build/guides/overriding-components/))
  change the chrome around content, not the content's shape. Not an enforcement mechanism.

The spec should pick one and say so; "documented but unenforced" is the default and is what the
map's ninety hand-written pages will drift toward otherwise.

## 4. Reusable content and partials

**There is no first-party partial primitive.** Starlight documents components, not content reuse
([using components](https://starlight.astro.build/components/using-components/)); the
authoring-content guide does not mention reuse at all.

The working mechanism is filesystem convention plus MDX imports, and one source detail makes it
work cleanly:

1. `docsLoader()` globs `**/[^_]*.{markdown,mdown,mkdn,mkd,mdwn,md,mdx}` — its JSDoc says it
   ignores _"filenames starting with `_`"_
   ([`loaders.ts`](https://github.com/withastro/starlight/blob/%40astrojs/starlight%400.41.3/packages/starlight/loaders.ts)).
   So `src/content/docs/_partials/foo.mdx` is **not** a page and gets no route.
2. Starlight's markdown pipeline decides what to process by **path prefix**, not by what the
   loader picked up: `getMarkdownProcessorPaths()` returns the docs collection directory, and
   `shouldTransformPath()` does `normalizedPath.startsWith(p)`
   ([`integrations/markdown-processor.ts`](https://github.com/withastro/starlight/blob/%40astrojs/starlight%400.41.3/packages/starlight/integrations/markdown-processor.ts)).

Together: **an underscore-prefixed partial inside `src/content/docs/` still gets asides, clickable
heading anchors and code-block RTL handling.** A partial placed outside that directory does not,
unless you add it to `markdown.processedDirs`:

```js
starlight({
  markdown: {
    processedDirs: ['./src/partials/'],
  },
})
```

`processedDirs` is `string[]`, default `[]`, paths relative to the project root
([configuration reference](https://starlight.astro.build/reference/configuration/#markdown)).

Consequences for the spec:

- Repeated warnings, the "Added in x.y" convention, install-command blocks, and any roster
  fragment shared by two pages can live in `src/content/docs/_partials/` and be imported.
- **Any page that imports a partial must be `.mdx`.** MDX imports do not exist in `.md`.
- MDX partials can take props, but they are plain MDX — `Astro.props` is not available; you read a
  `props` object. Frontmatter in a partial is inert YAML data, not page frontmatter.
- The alternative authoring format is **Markdoc** (`.mdoc`, via `@astrojs/markdoc` plus the
  Starlight Markdoc preset), where components need no import and use `{% card %}` tag syntax. This
  is a real option the map has not considered: it gives non-import component use and a stricter,
  less-escape-hatchy authoring surface, at the cost of MDX's arbitrary expressions. If the spec
  wants ninety pages that all look the same, Markdoc's constrained tag vocabulary is a mechanism
  for that in a way MDX is not.

Cloudflare's Starlight-based docs run ~1,200 partials on exactly this pattern, so it scales.

## 5. Code samples

Expressive Code `0.44.0` ships bundled and enabled (`expressiveCode: true` by default; set to
`false` to disable, or pass any
[EC configuration option](https://expressive-code.com/reference/configuration/)).

### What works in plain `.md` and `.mdx` alike

Default EC plugins are **frames, text markers and Shiki syntax highlighting**
([EC text markers](https://expressive-code.com/key-features/text-markers/)):

- **File titles / frames** — `` ```js title="src/blocks/hero.ts" ``, a `// path.js` comment on the first line, terminal framing for shell languages, `frame="none"` to opt out.
- **Line highlighting** — `{4}`, `{4-8}`, `{1, 4, 7-8}`.
- **Word and regex markers** — `"literal text"` or `/regex/`, each optionally prefixed `mark=`, `ins=` or `del=`.
- **Diffs** — `+`/`-` line prefixes, or `ins={2-4}` / `del={6}`; `` ```diff lang="js" `` keeps JS highlighting while showing diff markers.
- **Asides** — `:::note`, `:::tip`, `:::caution`, `:::danger`, with `:::tip[Custom title]` and `:::tip{icon="heart"}`.

### What is not bundled

**Line numbers and collapsible code sections are separate installs.** The Starlight `<Code>`
reference lists `showLineNumbers`, `startLineNumber` and `collapse` among its props because it
forwards everything to EC's Code component, but those props only do anything with
`@expressive-code/plugin-line-numbers` and `@expressive-code/plugin-collapsible-sections`
respectively. If the spec's roster pages want line numbers, that is one more dependency and one
more `expressiveCode` config block.

### Tabs

EC has no native code tabs. Starlight's `<Tabs>` / `<TabItem>` wrap code blocks, and `<Tabs>`
takes an optional `syncKey` that synchronises every tab group sharing that key **across page
navigations** ([tabs component](https://starlight.astro.build/components/tabs/)). `<TabItem>`
takes `label` (required) and `icon`. MDX or Markdoc only — not `.md`.

`syncKey` is worth a line in the spec: a single `syncKey="pkg"` convention makes the
npm/pnpm/yarn choice sticky sitewide, and `syncKey="runtime"` would do the same for
Cloudflare-vs-Node examples, which Plumix has a lot of.

### Sourcing samples from real files on disk

**Yes, first-party and documented** ([`<Code>` component](https://starlight.astro.build/components/code/)):

```mdx
import { Code } from '@astrojs/starlight/components';
import importedCode from '/tsconfig.json?raw';

<Code code={importedCode} lang="json" title="tsconfig.json" />
```

Vite's [`?raw` suffix](https://vite.dev/guide/assets#importing-asset-as-string) imports any file
as a string. Directly relevant to the map's open "code-sample policy" question: examples can live
in a real, type-checked fixture app in the monorepo and be pulled into the docs, and CI catches
the drift because the fixture is compiled.

Two limits:

- **Whole files only.** No first-party region markers or line-range selection. Slicing means doing
  it in the MDX component script (`raw.split('\n').slice(a, b).join('\n')`, fragile against edits)
  or writing a remark plugin. Several exist in the wild; none is a maintained Starlight plugin.
- **`.mdx` only**, since it needs an `import`.

Also available: `<FileTree>` for directory layouts, and `<Steps>` for numbered walkthroughs —
`<Steps>` maps almost exactly onto the "each page opens with its own quickstart walkthrough" half
of the map's page shape.

## 6. Search and i18n

### Search

**Pagefind ships by default, zero configuration** ([site search
guide](https://starlight.astro.build/guides/site-search/)). Pinned at `pagefind@1.5.2`;
`0.39.3` added support for Pagefind's `diacriticSimilarity` and `metaWeights` ranking options.

- Fully static: the index is built at build time and served as assets — it costs build time and
  bytes, nothing at runtime. `apps/docs` deploys as static assets to a Cloudflare custom domain
  (`wrangler.jsonc` has `assets.directory: "./dist"` and no Worker script), so this fits.
- **It requires prerendering.** `StarlightConfigSchema` carries
  `.refine((config) => !(!config.prerender && config.pagefind), 'Pagefind search is not supported with prerendering disabled.')`
  and `pagefind` defaults to `true` only when `prerender` is also true.
- Exclusions: `pagefind: false` in frontmatter for a whole page, `data-pagefind-ignore` on an
  element for part of one.
- Alternative: `@astrojs/starlight-docsearch` (first-party plugin, needs an Algolia account), or a
  community Typesense DocSearch plugin. Neither is needed for a ninety-page site.

Answering the map's open "docs-site search" question: **there is no decision to make.** It is on,
it works, and it costs nothing. The only spec-level choice is whether roster pages want
`data-pagefind-ignore` around their boilerplate so that item names rank above repeated prose.

### i18n

**First-party** ([i18n guide](https://starlight.astro.build/guides/i18n/)): routing, fallback
content, RTL, and pre-translated UI strings for roughly 34 locales — including `uk` and `ar`,
which is the launch set Plumix itself already ships.

Mechanics:

- `locales` + `defaultLocale` in config; a directory per locale under `src/content/docs/`.
- The `root` key serves one language without a URL prefix (`/about`, not `/en/about`), keeping its
  files directly in `src/content/docs/`.
- Untranslated pages **fall back to the default locale with a notice**, so translation can be
  partial from day one.
- Sidebar labels translate via `translations: { 'uk': '…' }` on config items, and UI strings via an
  `i18n` collection of JSON files in `src/content/i18n/`.

**The one decision that is expensive to defer:** if the site ever wants i18n, configure
`defaultLocale` with `root` **now**, while there is one placeholder page. Adding locales later to a
site that never declared one means either accepting a `/en/` prefix on every existing URL or
moving ninety files and eating the redirects. Declaring a root locale on day one costs nothing and
makes every later locale purely additive.

## Flags against the map's Notes

**Made awkward or impossible:**

- _"Section → page, never section → subsection → page."_ Starlight will not help. Group nesting is
  recursive and uncapped, `autogenerate.depth` is commented out in source, and any subdirectory
  becomes a third level automatically. Either write the sidebar manually (so a third level is a
  visible diff) or take on `starlight-auto-sidebar` for its `depth` property.
- _"A subsystem earns promotion… whose first page is named Getting Started."_ The promoted
  section's header is inert text; only its first page is clickable. Fine, but the spec should say
  it so nobody briefs a section landing page that Starlight can't route to.
- _"Ships with P1–P2 pages absent rather than stubbed."_ `draft: true` does this — but with a manual
  sidebar, a draft page still referenced by `slug` fails the build. Sidebar shape and tier are
  coupled; the spec must say which one drives.
- _"Rosters are hand-written and exhaustive… one file, ~60% roster."_ At the default ToC bounds
  (h2–h3), an exhaustive roster of `h3` items produces a ToC as long as the page. Set
  `maxHeadingLevel` deliberately.
- _"markdown-only, no custom `.astro` components"_ (`apps/docs/README.md`). Tabs, partials, `?raw`
  imports and inline `<Badge>` all require `.mdx`. The prettier/eslint premise in that README will
  need revisiting.
- _"No TypeDoc, no generated API appendix."_ Compatible with Starlight, but note the map's
  roster-drift worry has a partial answer in `?raw` code imports from a compiled fixture — samples
  can be guarded even where prose can't.

**Capabilities the map has not considered but should:**

- **Sidebar badges as tier markers.** `badge: { text: 'P1', class: 'tier-p1' }` renders the map's
  own tiering in the shipped sidebar, if that is wanted, or is at least available for "New" and
  "Experimental".
- **`draft: true`** as the mechanism for tiered shipping, rather than a convention about which
  files to create.
- **`starlight-links-validator`** as a build gate on internal links and heading anchors — the
  cheapest guard available against the cross-link half of roster drift.
- **`routeMiddleware`** as a real, supported build-time hook for enforcing page shape, if the spec
  wants the house template enforced rather than documented.
- **Markdoc** as an authoring format whose constrained tag vocabulary enforces uniformity across
  ninety pages in a way MDX cannot.
- **`<Steps>` and `syncKey`** — `<Steps>` fits the per-page quickstart half of the page shape
  exactly; `syncKey` makes package-manager and runtime choices sticky sitewide.
- **`markdown.processedDirs`** — the config knob that lets shared content live outside
  `src/content/docs/` and still get Starlight's pipeline.
- **A patch bump to `>=0.41.5`** before designing frontmatter, if the frontmatter schema uses unions
  or modified enums.
