`@plumix/plugin-feeds` is syndication: the XML a reader subscribes to and an aggregator polls. Installing it and configuring nothing serves RSS and Atom for the front page, for each entry type's archive, for each taxonomy term, for each author and for each date period, and puts a `<link rel="alternate">` in the head of every page that has one. A feed is its archive: it carries the entries the archive's page lists, from the same query.

## Overview

The plugin exports a factory named `feeds`. It takes no options, adds no database tables and ships no admin screens, so installing it is a package install and one array entry.

Feeds are not a search-engine concern, which is why they are their own package rather than part of `@plumix/plugin-seo`. A crawler does not need them; a reader does.

Nothing serves `/feed` until you install it. That is the boundary Plumix draws between core and a plugin: core owns what would be _wrong_ without a plugin installed, and a plugin owns what would merely be _absent_. A site with no feeds is a site with no feeds — it is not a broken one.

Every path below is claimed in the plugin's `afterSetup`, once every archive is registered: core lists each route an archive's page is served at, and the plugin claims `<route>/feed` beside each one. Nothing is guessed at from the shape of a request, which is what leaves a page slugged `feed` under some other prefix still rendering as content.

### The URLs it serves

Each row is RSS 2.0 at the path shown and Atom at that path plus `/atom`.

| Archive        | Path                      | Contents                                                      |
| -------------- | ------------------------- | ------------------------------------------------------------- |
| Front page     | `/feed`                   | Published entries of every non-hierarchical public type       |
| Entry type     | `/<archive slug>/feed`    | Published entries of that type                                |
| Taxonomy term  | `/<taxonomy>/<term>/feed` | Published entries of the taxonomy's public types on that term |
| Author         | `/authors/<slug>/feed`    | That author's published entries of non-hierarchical types     |
| Date           | `/YYYY[/MM[/DD]]/feed`    | Published entries of non-hierarchical types in the period     |
| Plugin archive | `<archive route>/feed`    | The archive's own `entries`                                   |

Each row is the archive page's own listing: the feed and the page read one entry query, so they cannot disagree about what the archive contains. A standalone page — an entry of a hierarchical type — is in its type's feed and its terms' feeds, and in none of the front page, author or date feeds, because it is on none of those pages.

`<archive slug>` is where the type's archive page is: its `hasArchive` slug, or its `rewrite.slug` when `hasArchive` is `true`. A type registered as `post` with `hasArchive: "articles"` syndicates at `/articles/feed`, and `/post/feed` is nothing. A type with no archive page — `hasArchive: false`, which is how `@plumix/plugin-blog` registers `post`, its posts listed on the front page instead — has no feed of its own; its entries are in `/feed`.

Twenty items, newest publish time first, whatever order the archive's page lists them in — that is what a subscriber's reader assumes. An archive that resolves to nothing — a term slug nothing matches, an author nobody is, an impossible date such as `2026/02/30` — is a 404 rather than an empty feed, as its page is.

A term feed sits directly under the term's own archive, wherever that is: a hierarchical taxonomy addresses a nested term at its full path (`/region/europe/france/feed`), a flat one at its slug alone.

<Aside type="note" title="A private site has no feeds">
  With `public` off in site settings every feed is a 404 and no page advertises
  one. The sitemap serves an empty 200 instead, because an empty sitemap is a
  meaningful answer and an empty feed is not.
</Aside>

  </TabItem>
  <TabItem label="npm">

```sh
npm install @plumix/plugin-feeds
```

  </TabItem>
  <TabItem label="yarn">

```sh
yarn add @plumix/plugin-feeds
```

  </TabItem>
  <TabItem label="bun">

```sh
bun add @plumix/plugin-feeds
```

  </TabItem>

Then:

<Steps>

1. **Add `feeds()` to the `plugins` array.** Its position there does not matter — see below.

   ```ts no-typecheck
   import { plumix } from "plumix";

   import { blog } from "@plumix/plugin-blog";
   import { feeds } from "@plumix/plugin-feeds";

   import { theme } from "./theme";

   export default plumix({
     plugins: [blog(), feeds()],
     theme,
   });
   ```

2. **Restart the dev server.**

   ```sh
   pnpm dev
   ```

3. **Read one.** `/feed` is the front page's posts, `/category/<term>/feed` is one category's, and `/feed/atom` is the same items as Atom.

</Steps>

Array order does not decide what gets a feed. The plugin reads the registry once, in `afterSetup`, which runs after every plugin's `setup` — so it sees `blog`'s archives wherever `blog()` sits. The one thing it cannot see is an archive another plugin registers from its own `afterSetup` when that plugin is listed later, which is a reason to register in `setup`.

## Discovery links

The plugin subscribes to `render:document` and appends the page's own feed, both formats:

```html
<link
  rel="alternate"
  type="application/rss+xml"
  href="https://example.com/feed"
/>
<link
  rel="alternate"
  type="application/atom+xml"
  href="https://example.com/feed/atom"
/>
```

A page advertises the feed of the archive that owns it. Core answers which archive that is, for the page's URL, from the same table the router matched — so the head points at exactly the feed that serves those entries. A later page advertises the feed of the listing it paginates: `/category/news/page/2` points a reader at `/category/news/feed`.

A single entry, the search page and an error page belong to no archive, so they advertise nothing.

It gap-fills. A theme or another plugin that already set an `alternate` of a given type keeps it, and only the missing format is added.

## Adjusting the items

`feed:items` runs over the collected list before serialization, with the scope the items were collected for. Add, drop or re-order:

```ts no-typecheck
import { definePlugin } from "plumix/plugin";

export const featured = definePlugin("featured", {
  setup: (ctx) => {
    ctx.addFilter("feed:items", (items, scope) =>
      scope.archive.kind === "front-page" ? items.slice(0, 5) : items,
    );
  },
});
```

`scope.archive` names the archive as core's lookup does — `front-page`, `archive` (with its `entryType`), `taxonomy` (with its `taxonomy`), `author`, `date`, or `custom` (with the plugin archive's `name`) — and `scope.params` holds what its route captured.

The plugin's own package must be installed for the hook name to type-check — it declares `feed:items` on `FilterRegistry` through the single `plumix` augmentation specifier, the same way every plugin declares a hook.

## Syndicating a plugin archive

`registerArchiveType` takes an optional `feed`, and that field is this plugin's augmentation rather than a core one — declare it and it type-checks once `@plumix/plugin-feeds` is a dependency. It is only accepted beside `entries`: the feed is the archive's own entry query, so an archive with no `entries` has nothing a feed could read, and the types refuse it.

```ts no-typecheck
import { definePlugin } from "plumix/plugin";

import "@plumix/plugin-feeds";

export const events = definePlugin("events", {
  setup: (ctx) => {
    ctx.registerArchiveType("event-series", {
      routes: ["/events/:series"],
      entries: (q, params) =>
        q.ofTypes("event").inTerm("event-series", params.series ?? ""),
      title: (params) => `Series: ${params.series ?? ""}`,
      feed: true,
    });
  },
});
```

`feed` is `true`, or an object reserved for feed-only options, of which there are none yet. There is nothing else to declare: the entries are the archive's, and a feed that needs a different set is a different archive.

The feed carries what the page lists, newest first and capped at twenty, whatever order `entries` gives the page. The query `entries` receives already holds only public entries, and the feed applies that rule again when it compiles the query, so an archive that builds a query from scratch still cannot syndicate a draft.

The feed paths follow from the archive's routes, so there is nothing to keep in step. Each route gains a feed at `<route>/feed` and Atom at `<route>/feed/atom`: `/events/summer` syndicates at `/events/summer/feed`. The `/page/:page` form core derives for each route is a later page of a listing rather than a listing of its own, so it gets no feed, and its pages advertise the feed of the route they paginate.

Params `entries` answers `null` for are a 404 on the page and the feed together, and the page advertises nothing. Because `entries` records intent rather than resolving it, a page asking whether it has a feed costs no query.

An archive declaring an `access` policy gets no feed at all. A feed is a registered public route, which core answers ahead of the access gate and ahead of loading a principal, so there is no reader there to check a policy against — serving one would hand the archive's entries to anyone who asked.

Two archives can match one URL. A feed is served only where the feed route that answers it belongs to the archive whose page is there: a `/:section` archive outranking a type archive at `/news` owns the page at `/news`, but the type's literal `/news/feed` route answers that feed URL, so it is a 404 and the page advertises nothing rather than a feed of different entries.
