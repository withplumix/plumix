`@plumix/plugin-feeds` is syndication: the XML a reader subscribes to and an aggregator polls. Installing it and configuring nothing serves RSS and Atom for the whole site, for each entry type, for each taxonomy term, for each author and for each date period, and puts a `<link rel="alternate">` in the head of every page that has one.

## Overview

The plugin exports a factory named `feeds`. It takes no options, adds no database tables and ships no admin screens, so installing it is a package install and one array entry.

Feeds are not a search-engine concern, which is why they are their own package rather than part of `@plumix/plugin-seo`. A crawler does not need them; a reader does.

Nothing serves `/feed` until you install it. That is the boundary Plumix draws between core and a plugin: core owns what would be _wrong_ without a plugin installed, and a plugin owns what would merely be _absent_. A site with no feeds is a site with no feeds — it is not a broken one.

Every path below is claimed in the plugin's `afterSetup`, once every entry type and taxonomy is registered, so the plugin enumerates them and registers concrete routes. Nothing is guessed at from the shape of a request, which is what leaves a page slugged `feed` under some other prefix still rendering as content.

### The URLs it serves

Each row is RSS 2.0 at the path shown and Atom at that path plus `/atom`.

| Scope          | Path                      | Contents                                    |
| -------------- | ------------------------- | ------------------------------------------- |
| Site           | `/feed`                   | Published entries of every public type      |
| Entry type     | `/<type>/feed`            | Published entries of that type              |
| Taxonomy term  | `/<taxonomy>/<term>/feed` | Published entries attached to that term     |
| Author         | `/authors/<slug>/feed`    | That author's published entries             |
| Date           | `/YYYY[/MM[/DD]]/feed`    | Published entries in the period             |
| Plugin archive | `<archive route>/feed`    | Whatever the archive's own scope narrows to |

`<type>` is the registered entry-type name, not its `rewrite.slug` — a type registered as `post` and mounted at `/articles` still syndicates at `/post/feed`, which is what the archive page advertises.

Twenty items, newest publish time first. A scope that resolves to nothing addressable — an unregistered entry type, a term slug nothing matches, an impossible date such as `2026/02/30` — is a 404 rather than an empty feed.

A term feed sits directly under the term's own archive. A hierarchical taxonomy addresses a nested term at its full path (`/region/europe/france/feed`); a flat one addresses one segment, and a term parented inside a flat taxonomy therefore has an archive but no feed — the archive page advertises none, so the two agree.

<Aside type="note" title="A private site has no feeds">
  With `public` off in site settings every feed is a 404 and no page advertises
  one. The sitemap serves an empty 200 instead, because an empty sitemap is a
  meaningful answer and an empty feed is not.
</Aside>

  <TabItem label="bun">


Then:

<Steps>

1. **Add `feeds()` to the `plugins` array.** Its position there does not matter — see below.

   ```ts no-typecheck
   import { plumix } from "plumix";

   import { blog } from "@plumix/plugin-blog";
   import { feeds } from "@plumix/plugin-feeds";

   import { theme } from "./theme";

   export default plumix({
     plugins: [blog(), feeds()],
     theme,
   });
   ```

2. **Restart the dev server.**

   ```sh
   pnpm dev
   ```

3. **Read one.** `/feed` is the whole site, `/post/feed` is the blog, and `/feed/atom` is the same items as Atom.

</Steps>

Array order does not decide what gets a feed. The plugin reads the registry once, in `afterSetup`, which runs after every plugin's `setup` — so it sees `blog`'s entry types wherever `blog()` sits. The one thing it cannot see is a type another plugin registers from its own `afterSetup` when that plugin is listed later, which is a reason to register in `setup`.

## Discovery links

The plugin subscribes to `render:document` and appends the page's own feed, both formats:

```html
<link
  rel="alternate"
  type="application/rss+xml"
  href="https://example.com/feed"
/>
<link
  rel="alternate"
  type="application/atom+xml"
  href="https://example.com/feed/atom"
/>
```

Which feed a page advertises follows what the page is. An archive advertises its type's feed, a term archive its term's, an author archive that author's, a date archive that period's, and a plugin archive the feed under the route it matched. A single entry advertises the **site** feed rather than its type's: someone subscribing from an article wants everything new, which is the convention every comparable CMS follows.

Two page kinds advertise nothing: a search page is thin, and an error page is not content.

It gap-fills. A theme or another plugin that already set an `alternate` of a given type keeps it, and only the missing format is added.

## Adjusting the items

`feed:items` runs over the collected list before serialization, with the scope the items were collected for. Add, drop or re-order:

```ts no-typecheck
import { definePlugin } from "plumix/plugin";

export const featured = definePlugin("featured", {
  setup: (ctx) => {
    ctx.addFilter("feed:items", (items, scope) =>
      scope.kind === "site" ? items.slice(0, 5) : items,
    );
  },
});
```

The plugin's own package must be installed for the hook name to type-check — it declares `feed:items` on `FilterRegistry` through the single `plumix` augmentation specifier, the same way every plugin declares a hook.

## Syndicating a plugin archive

`registerArchiveType` takes an optional `feed`, and that field is this plugin's augmentation rather than a core one — declare it and it type-checks once `@plumix/plugin-feeds` is a dependency. `scope` narrows the entries the feed carries, or answers `null` for a 404, from the params the archive's route captured:

```ts no-typecheck
import { definePlugin, FRAMEWORK_PAGINATION_SUFFIX } from "plumix/plugin";

import "@plumix/plugin-feeds";

export const events = definePlugin("events", {
  setup: (ctx) => {
    ctx.registerArchiveType("event-series", {
      routes: [
        "/events/:series",
        `/events/:series${FRAMEWORK_PAGINATION_SUFFIX}`,
      ],
      resolve: (_ctx, params) => ({
        data: { kind: "custom", name: "event-series" },
        title: `Series: ${params.series}`,
      }),
      feed: {
        scope: (q, params) =>
          q.ofTypes("event").inTerm("event-series", params.series ?? ""),
      },
    });
  },
});
```

The query `scope` receives is already restricted to published entries of public types, and every method on it adds a condition. Nothing on it removes one, so the visibility rule is the plugin's rather than yours to remember: an archive that forgets to narrow gets a feed of fewer entries than it meant, never a feed of drafts.

`ofTypes`, `inTerm`, `byAuthor`, `inDateRange` and `under` cover how archives usually model a subject. For anything they do not reach — a meta column, a join of your own — `where(sql)` ANDs an arbitrary predicate on, and cannot widen the feed either — so long as it is built from the `sql` template rather than `sql.raw`, which never interpolates a route param safely anyway. Returning `q.none()` is a feed that exists and is empty; returning `null` is a feed that does not exist.

A scope records what to narrow by instead of resolving it, so building one runs no queries. The term path in the example above is resolved when the feed is served.

An archive declaring an `access` policy gets no feed at all. A feed is a registered public route, which core answers ahead of the access gate and ahead of loading a principal, so there is no reader there to check a policy against — serving one would hand the archive's entries to anyone who asked.

The feed paths follow from the archive's routes, so there is nothing to declare and nothing to keep in step. Each route gains a feed at `<route>/feed` and Atom at `<route>/feed/atom`: `/events/summer` syndicates at `/events/summer/feed`. A route ending in `FRAMEWORK_PAGINATION_SUFFIX` is a later page of a listing rather than a listing of its own, so it gets no feed — declare later pages with that suffix, the shape core's own archives use, so the plugin can tell them apart. Core matches an archive's suffixed routes ahead of its others, so a multi-segment capture such as `/docs/:path+` does not swallow `/page/2`.

Every page of the archive advertises its feed, gap-filled like any other page's. A later page advertises the feed of the route it paginates, so `/events/summer/page/2` points a reader at `/events/summer/feed`. The head asks `scope` the same question the feed route does, so a page whose `scope` answers `null` advertises nothing and its feed is a 404. That puts `scope` on every render of the archive's pages as well as on its feed. Because a scope only records intent, asking costs no query — and for the same reason the head cannot see a narrowing that fails only once it is resolved, such as a term slug nothing answers to. That page advertises a feed that 404s. Answer `null` for params the archive cannot place, as its own `resolve` should, and the page and its feed 404 together. Answer `null` rather than throw, too: a throw fails the page, not just the feed.

Two feeds cannot share a path. Where an archive route's feed path is one another feed already claims — an archive at `/events` beside an entry type named `events` — the first claim keeps serving. The head asks the question per URL: wherever another feed's route also answers the page's feed URL — `/:section` on `/news` beside a type named `news` — the archive advertises nothing rather than pointing its readers at a feed of different entries.
